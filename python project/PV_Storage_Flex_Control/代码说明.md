## 第 0 章 · 先读这个（30 秒版）

**这个工程是什么**：一个 Python 程序包 `pvflex`，把本园区的**真实**光伏发电、用电、电价、碳数据，算成"储能该怎么充放电最省钱、最减碳"的方案。

**它现在有多真**：吃的是本园区 2025 年真实数据（8760 小时光伏 + 219 天用电 + 真实电费账单），**只有一个参数还是估算的——储能容量**。

**如果你时间很紧，只做三件事**：

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | 拿到**储能容量（kWh）** | 唯一还差的关键数据。改 `config.py` 一行、重跑，结果即定稿 |
| 2 | 跑一次 `python run_extension_study.py` | 论文/汇报的所有数字来源，不跑就只有基础统计 |
| 3 | 记住**两个消纳率要区分**：41.91%（部分计量点）vs 18.35%（园区全量） | 引用时不写口径会被问倒 |

**四步理解全流程**：读数据 → 猜未来（预测）→ 做决定（调度电池）→ 算成绩（省钱多少、减碳多少）。

# 第一层：给零基础的你

## 第 1 章 · 这个工程是干什么的

### 1.1 一句话版

这是一个**帮"装了太阳能板 + 大电池的工厂园区"省电费、减碳排的电脑程序**。

它做的事情，用人话讲就是四步：

1. **读数据**：把园区真实的光伏发电量、每天用电量读进来。
2. **猜未来**：预测"明天大概发多少电、用多少电"（猜得越准越好）。
3. **做决定**：根据预测，决定"电池什么时候充电、什么时候放电"，让园区尽量多用自己发的便宜电、少从电网买贵电。
4. **算成绩**：算一算，用了这个策略之后，比"什么都不做"**省了多少钱、少排了多少二氧化碳**。

整个程序是用 Python 写的。你不用会写，只要会"按几个命令运行它"就行。

> 📌 **一句话记住它现在有多真**：这个程序吃的已经是**本园区 2025 年的真实数据**，
> 只有**储能容量**这一个数还是估算的。详见第 5 章。

### 1.2 技术版

**对应科研任务**：硕士学位课题《面向烟草绿色园区的光储直流微电网能碳协同智能调控系统》中的**研究方向 3（多时间尺度"能-碳"指标智能调控）**。

**代码做四件事**：

| 编号 | 做什么 | 对应模块 | 产出 |
|---|---|---|---|
| 方案B | 项目数据统计分析 | `analysis/` | 年发电 / 年用电 / 消纳率 / 电费 |
| 方面1 | 源-荷多时间尺度预测 | `forecasting/` | 明日逐时发电与用电预测 |
| 方面2 | 鲁棒优化 + 随机规划调控 | `optimization/` | 电池充放电计划 + 省钱减碳量 |
| 方面3 | 大数据挖掘 + 云边协同框架 | `mining/` | 典型日 / 相关性 / 异常日 / 架构演示 |
| 辅助 | 碳核算 + 仿真背景参数 | `carbon/` `simulation/` | 碳指标 dict / Simulink 参数字典 |

**与申报书硬指标对照**：

| 申报书条款 | 要求 | 代码现状 |
|---|---|---|
| 十四(二)(1) | 预测准确率月均方根误差 < 20% | PV 相对 RMSE **13.21%** ✅ 达标；负荷受分时数据缺失限制（见 §5.5） |
| 十一(一)2 / 技术关键(2) | 确定最优直流电压等级序列 | `config.DC_VOLTAGE_LEVELS_V=[700,48]V`，与 Simulink 双母线一致，方向3 运行即打印 |
| 十一(一)1 | 源-荷-储一体化（消纳率） | 方向3 汇总直接给出全期光伏消纳率（18.35%），纳入能-碳汇报 |
| 创新点(3) | 自适应日内修正 + 模型更新 | `forecast.run_realtime_adaptive()`：演示日滚动窗口再训练，方向3 打印对比 |

## 第 2 章 · 名词扫盲

### 2.1 基础词

| 词 | 大白话解释 |
|---|---|
| **PV / 光伏** | 就是太阳能板发的电。"PV 发电量"= 太阳能板发了多少度电。 |
| **负荷** | 园区用掉的电。"负荷曲线"= 一天里每个小时用了多少电。 |
| **储能 / 电池** | 一块大充电宝。电多的时候存起来，电贵/不够的时候放出来用。 |
| **消纳率** | 自己发的电里，**自己用掉了多少**。消纳率高 = 没浪费太阳能。比如消纳率 90% 表示发了 100 度电，90 度自己用了，10 度卖回电网。 |
| **调度（Dispatch）** | 决定"电池每一刻该充电还是放电、从电网买不买电"的一套计划。 |
| **日前调度** | 今天提前给"明天一整天"定好计划（像前一天晚上列好明天作息表）。 |
| **实时 / MPC** | 模型预测控制。每个小时都"看一眼未来的预测 + 刚才实际发生了什么"，再决定这一小时怎么动。比日前更灵活（像边走边看路）。 |
| **鲁棒 / 随机** | 两种"应对预测不准"的思路。因为预测永远有误差，这两种方法让调度别因为猜错而翻车。 |
| **预测（Forecast）** | 猜未来。代码里预测的是"明天发多少电、用多少电"。 |
| **RMSE / MAE / sMAPE** | 三个"猜得准不准"的分数。**数值越小 = 猜得越准**。论文里用它们比哪种预测方法好。 |
| **消融（Ablation）** | 像做实验：把方法的某个零件拆掉，看成绩掉不掉。掉了 = 这个零件有用；没掉 = 没用。 |
| **敏感性分析** | 改一个参数（比如电池造大一点），看最终结果变多少。用来知道"哪些参数影响大"。 |
| **置信区间（CI）** | 结果不是一个数，而是一个范围。比如"省 5.18%，有 95% 把握在 4.16%~6.58% 之间"。 |
| **基线（Baseline）** | 用来对比的"啥也不做"或"最简单方法"。你的方法比基线好，才算有贡献。 |
| **SOTA** | "当前最好水平"的缩写。意思是拿你的方法和目前公认最强的对手比。 |
| **SCI 论文** | 一种国际认可的学术期刊论文。导师希望用这个项目产出一篇。 |

### 2.2 与"数据"有关的词（最容易出错的一类）

| 词 | 大白话解释 |
|---|---|
| **口径** | 就是"这个数字是在多大范围内统计的"。同一个词"用电量"，范围是"几栋楼的末端电表"和"整个园区含高压总表"，数值能差 3 倍。**本项目最容易出错的地方就是口径混用。** |
| **高压进线总表** | 园区从电网进电的"总闸"上的表，记的是全园区用电。 |
| **末端表** | 某一栋楼、某一条线路上的小表，只记局部用电。 |
| **逐时 / 8760h** | 一年有 365×24 = 8760 小时。"8760h 数据"= 每小时都有一条记录，是最精细的数据。 |
| **编码（GBK / UTF-8）** | 中文文字在电脑里存成二进制的方式，有不同标准。**如果程序猜错了编码，整份文件的内容就是乱码或读不出来。** 本项目就是踩过这个坑（见 §6.2）。 |
| **归一化** | 把一串数字成比例地缩放，让它们加起来等于 1。这样得到的就变成"占比"而不是"电量"。 |
| **量纲** | 数字的"单位"。电量是 kWh、占比是无单位的纯数字。**两者混用会差几百倍。** |
| **锚定** | 用自己的数据算出"形状"，再用一个权威的总数把它整体缩放，让合计对上。 |
| **数据泄漏** | 训练模型时不小心让模型"偷看"了它本该预测的未来数据，导致精度虚高、实盘必崩。本项目专门修过这个（见 §8.5）。 |
| **凸性** | 一个数学性质。有它，优化问题就能又快又稳地求出唯一解。本项目靠"上网价 ≤ 最低买价"来保证（见 §8.6）。 |

### 2.3 英文模型名

> - **LSTM / Transformer / N-BEATS**：三种"深度学习"预测模型。代码里 `forecasting/deep.py` 实现了它们。
>   - LSTM 像"有记忆的曲线追踪器"；Transformer 会自动找出历史上相似的日期（GPT 同家族）；N-BEATS 是专为时间序列设计的。
> - **XGBoost**：另一种从数据学规律的模型，比深度学习"轻量"，跑得快。
> - **KMeans**：一种"自动分组"的方法。本项目用它把一年 365 天按发电曲线相似度分成 8 类。
> - **PuLP / CBC / scipy linprog**：三种优化求解器（算"最优方案"的工具）。

## 第 4 章 · 怎么跑起来

> 前提：电脑上已装好 conda 环境 `PV_Storage_Flex_Control`（含 xlrd/openpyxl/numpy/pandas/scipy/pypdf/torch/pulp）。

### 4.1 第一次用：环境准备

```bash
# ① 打开 Anaconda Prompt（不是普通 cmd），进入工程目录
cd "<仓库根>\python project\PV_Storage_Flex_Control"

# ② 激活环用环境（激活后命令行前面会出现 (PV_Storage_Flex_Control) 字样）
conda activate PV_Storage_Flex_Control

# ③ 换电脑时才需要：安装依赖 + 把工程装成可编辑包
pip install -r requirements.txt
pip install -e .
```

装完 `pip install -e .` 后，任意位置都能 `python -m pvflex.cli` 运行。

### 4.2 六种运行模式

```bash
python -m pvflex.cli                     # 全部（= stats + direction3），约 1 分钟
python -m pvflex.cli --mode stats        # 只跑方案B统计，秒级
python -m pvflex.cli --mode direction3   # 只跑方向3三方面，约 1 分钟
python -m pvflex.cli --mode netload      # 净购电小时曲线还原（需几百个PDF）
python -m pvflex.cli --mode benchmark    # 预测基线对比+消融，几分钟
python -m pvflex.cli --mode rolling      # 全年滚动+敏感性，几分钟

python run_extension_study.py            # 一键跑 benchmark + rolling，存 JSON，约 5 分钟
```

> 🔴 **最容易踩的坑**：敲 `python -m pvflex.cli` **不会**跑 benchmark 和 rolling。
> 这两个是重活（训多个深度学习模型 / 上千次优化求解），设计成"想跑才手动指定"。
> **如果你奇怪"怎么没看到论文里那些数字"（SOTA 对比表、全年省 5.18%），原因就在这里。**
> 解决办法：另加 `--mode benchmark` / `--mode rolling`，或直接跑 `python run_extension_study.py`。

各模式对应的流程编号与论文位置：

| 模式 | 流程 | 对应论文哪部分 |
|---|---|---|
| `stats` | 方案B | 数据画像（Results 4.1） |
| `direction3` | 方面1+2+3 | 方法（3.2–3.4）+ 案例（4.2–4.4） |
| `netload` | 净购电还原 | 数据（2.2） |
| `benchmark` | SOTA 对比+消融 | 结果（4.2 扩展） |
| `rolling` | 全年滚动+敏感性 | 结果（4.3 扩展）+ 讨论（5） |

### 5.4 两个"消纳率"不要混用（🔴 必看）

项目里存在两个消纳率数字，**含义不同、都不算错**：

| 数字 | 统计范围 | 出处 |
|---|---|---|
| **41.91 %** | 只统计了部分计量点（约占总用电 36%） | 项目方 `福州烟草-消纳率计算.xlsx` |
| **18.35 %** | 园区全量口径 | 本程序输出（能耗平台 219 天） |

分母范围差了 3 倍，所以数字差这么多。**引用时一定要写清是哪个口径**，
否则会被问"你自己两个数都对不上"。

> 📌 **通用原则**：**形状与总量要解耦**。
> 分时形状（归一化后的占比）可以跨口径使用；**总量必须用对应口径的数据源**。

### 5.5 为什么负荷预测误差天生比光伏大？

| | 光伏 | 负荷 |
|---|---|---|
| 物理规律 | 有（太阳升落、阴天少发） | 弱（人的行为 + 设备启停） |
| 我们有的数据 | 8760h 逐时实测 | **只有日总量**，要摊成 24h 就是猜 |
| 相对 RMSE | 5~6% | 30~43% |

根因是**数据粒度限制**，不是模型失效：

- 当前小时级负荷 = **日总量 × 实测 24h 形状**
- 日总量来自能耗平台**日采集**，无法复原该日真实的逐时波动
- 模型只能学到"同月同时刻的历史均值 × 当日总量水平"，小时级绝对量必然存在偏差

> 📌 **论文里不要硬吹负荷预测精度**，而要老实说明"受数据分辨率限制"，
> 并把"向园区申请逐时电量表"列为下一步改进方向。这样说反而更可信。
> 本次把形状从"估算"换成"8760h 实测"已是在现有数据条件下的最优解。

### 5.6 拿到真实储能容量后怎么改

只改 `config.py` 里这两行，**其他代码一行都不用动**，重跑即可：

```python
BATTERY_CAPACITY_KWH = 1000.0    # ← 改成设计院给的真实值
BATTERY_POWER_KW = 500.0         # ← 功率也按实际改
```

改完务必跑一次回归（见 §13.3）。

## 第 6 章 · 常见报错与怎么办

| 现象 | 大概率是 | 怎么办 |
|---|---|---|
| `conda: 无法识别` / `command not found` | 没装 Anaconda，或终端不对 | 用 **Anaconda Prompt** 打开，别用普通 cmd |
| `Could not find conda environment` | 环境名不对 | 先运行 `conda env list` 看真实环境名 |
| `ModuleNotFoundError: No module named 'pvflex'` | 没在正确文件夹 / 没激活环境 | 确认 §4.1 第 ①②步都做了 |
| `No module named 'pypdf'` | 读 PDF 的库没装 | 运行 `pip install pypdf`（不影响主流程） |
| 跑出来数字全是 0 或很怪 | 数据路径对不上 | 看 `config.py` 里 `REPO_DATA_DIR` 是否指向真实"数据资料"文件夹 |
| 报 `ModuleNotFoundError: No module named 'pandas'`（但你明明装了） | **用错了 Python** | 见 §6.1，这是本项目最容易犯的错 |
| 负荷天数不是 219 天 | 数据文件被改动过 | 见 §6.2 |
| 中文显示成一堆方框 □□□ | 画图没找到中文字体 | 一般不影响结果，换台电脑重跑即可 |

### 6.1 🔴 最容易犯的错：用错 Python

你电脑上有**两个** Python：

| | 路径 | 有没有装依赖 |
|---|---|---|
| 系统 Python | `C:\Program Files\Python313\python.exe` | ❌ **没装**，是个空壳 |
| conda 环境 | `<conda环境>\python.exe` | ✅ 装齐了 |

如果看到报错说"没有 pandas / numpy / torch"，**先怀疑自己用错了 Python**，
而不是以为依赖没装。正确做法就是老老实实先 `conda activate PV_Storage_Flex_Control`。

> ⚠️ **不要**用 `C:\Program Files\Python313\python.exe 你的脚本.py` 这种全路径写法，
> 那个 Python 里什么都没有，必然报错 —— 而且报错信息会误导你以为是代码问题。

### 6.2 🔴 第二容易犯的错：负荷天数不对

正常是 **219 天**。如果你看到别的数字：

- **变多了（比如 365）**：有人把 `config.py` 里的 `LOAD_DROP_UNRELIABLE` 改成了 `False`，
  或者放宽了 `LOAD_RELIABLE_START/END`。
  ⚠️ **不要把区间放宽**：2025-11 到 2026-04 那几个月，能耗平台**没有导出高压进线总表**，
  只剩末端照明/插座表，用电量只有正常月份的 4%。放进来会让年用电量严重偏低。
- **变少了（比如 48）**：数据文件真的缺了，或者路径指错了。

> 📌 **怎么自己判断某个月的数据能不能用？**（这是本项目最实用的一个方法）
> 不要只看"总电量突然变小"，而要看**这个月有哪些计量点、各多少电**：
> - 正常月的第一名是 `配电房-低压柜`（这是高压进线总表），单点月电量 10~47 万 kWh
> - 异常月的第一名变成 `综合用房`、`2APxx`（这些是末端小表），单点只有几百~1.5 万 kWh
>
> 差 30 倍以上就说明：**不是用电量真的降了，而是总表根本没导出到这份数据里。**
> 前者要改模型，后者只能去能耗平台补数据 —— 处理方向完全不同。

### 6.3 通用原则

**报错先看最后一行红字**，它通常已经告诉你缺什么。看不懂就把整段红字发给帮你的人。

## 第 8 章 · 模块详解

### 8.1 `cli.py` —— 命令行总开关

**职责**：按正确顺序调用各模块，打印进度，不做任何实际计算。

| 函数 | 作用 | 耗时 |
|---|---|---|
| `run_stats()` | 方案B：发电/负荷/消纳率/电费 + 5 张图 | 秒级 |
| `run_direction3()` | 方向3：预测 → 优化 → 挖掘，三个方面串起来 | ~1 分钟 |
| `run_benchmark()` | 预测 SOTA 对比 + 消融 | 几分钟 |
| `run_rolling()` | 全年滚动评估 + 3 类敏感性 | 几分钟 |
| `run_netload()` | 净购电逐时曲线还原（账单锚定法） | 视 PDF 数量 |
| `_pick_representative_day()` | 挑"日均发电量为中位数"的那天做演示日 | 毫秒级 |
| `_save_direction3_figures()` | 存方向3 的 3 张示意图（matplotlib 缺失则优雅跳过） | 秒级 |

**为什么 `run_stats` 里电费要用"消纳同口径的期内用电"？**
因为光伏只有 219 天数据，用电量也是 219 天。如果拿"219 天的光伏节省"去除"365 天的全年电费"，
比例会被摊薄、看着很小，但这不是光伏效果差，而是两个数天数对不上（口径不一致）。
同口径后满足 `节省 ÷ 电费 ≡ 自消纳率`（实测 0.186 = 0.186）。

**代表日选取增加了 24h 完整性校验**：原逻辑从所有日中按中位数取代表日，
但不完整日（<24 小时）会导致后续优化器维度不匹配。现增加 `counts == 24` 过滤，
仅从完整日中选取。

### 8.2 `config.py` —— 配置中心

**职责**：所有"经常要改、且跟着项目走"的参数。**改参数只改这一个文件。**

**参数分三组**：

| 组别 | 代表参数 | 状态 |
|---|---|---|
| 路径 | `REPO_DATA_DIR` / `PV_GEN_CSV` / `LOAD_DIR` | ✅ 自动推导，一般不用改 |

> 🔴 **唯一的硬缺口**：储能容量 kWh 无确切值（排查过程见 §5.2）。
> 敏感性分析已扫 250~2000 kWh 区间（省电费 1.403% → 10.737%），结论方向不翻，
> 但报告中必须写明"此结果为 1000kWh 假设下"。

`LOAD_DAY_MIN_FRAC`（0.10）。主要判据已改为**按可靠区间显式截断**。
⚠️ 注意：若把 `LOAD_MONTH_MIN_FRAC` 从 0.25 调到 0.10，2025-11（部分缺失月）就会被放进来污染数据。

**为什么分两个电压等级**：700V 带大功率设备（空调、动力），48V 带照明和小负载。
分压是为了减少转换级数和损耗 —— 这正是"直流直连"创新点的物理基础。

**🔴 本文件踩过的最大的坑：编码不统一导致整月数据静默丢失**

能耗平台导出的 CSV 混有两种编码：
- GBK：`20250804/06/08.csv`、`25.03.csv`、`26.02.24.csv`
- UTF-8-sig：其余 130+ 个文件

原代码写死 `encoding='utf-8-sig'`，异常被 `try/except` 降级为 warning 后**静默跳过整月**。
更隐蔽的是：GBK 文件读出来的首列会多一个 `Unnamed: 0` 空索引列，
把"名称"列挤到第 2 列，导致列名定位失败。

现在的做法：

```python
_CSV_ENCODINGS = ('utf-8-sig', 'gbk', 'gb18030', 'latin1')

def _read_csv_any_encoding(path, **kwargs):
    for enc in _CSV_ENCODINGS:
        try:
            df = pd.read_csv(path, encoding=enc, **kwargs)
            cols = [str(c) for c in df.columns]
            if len(cols) >= 2 and cols[0].startswith('Unnamed') and cols[1].strip() == '名称':
                df = df.iloc[:, 1:]      # 丢掉空列，扶正"名称"
            return df, enc
        except (UnicodeDecodeError, UnicodeError) as e:
            last_err = e
            continue
    raise last_err if last_err else RuntimeError(f'无法读取 CSV：{path}')
```

### 8.5 `analysis/stats.py` —— 项目统计

| 函数对 | 算什么 |
|---|---|
| `analyze_pv` / `print_pv_summary` | 年发电、日均、峰谷、**容量系数** |
| `analyze_load` / `print_load_summary` | 年用电、日均、峰谷、**日负荷率** |
| `calc_consumption_rate` / `print_consumption_summary` | **光伏消纳率** |
| `calc_cost` / `print_cost_summary` | 电费与光伏收益（简化） |
| `make_figures()` | 5 张分析图 |

**两个关键指标的含义**：

- **容量系数** = 年发电 ÷ (额定容量 × 8760)。福建属三类光照区，正常 12%~22%。
  **当体检指标用**：算出来远大于 25% → 额定容量填小了；只有 5% → 发电量数据可能缺了大半。
  当前实测 **14.38%**，处于合理区间 ✅
  > ⚠️ 注意区分"配电容量"和"光伏装机容量"：DWG 里的 `900kW×7 = 6.3MVA` 是**配电变压器**容量，
  > 不是光伏装机。把 6300 填进 `PV_RATED_KW` 会让容量系数失真到 4%。
- **日负荷率** = 日均用电 ÷ 最大日用电。越接近 1 表示用电越平稳。
  当前 **53.61%**，说明园区用电有一定波动（这正是储能削峰填谷的价值所在）。

**消纳率算法**（已与项目方口径对齐）：

```
被消纳的用电量 = 用电量 − max(0, 用电量 − 发电量) = min(用电量, 发电量)
消纳率         = 被消纳的用电量 ÷ 用电量
```

用大白话讲这个公式：
- 当**光伏少于用电**（发电量 < 用电量）：发的电全被自己用掉了 → 被消纳 = 发电量
- 当**光伏多于用电**（发电量 > 用电量）：最多只能消纳掉全部用电 → 被消纳 = 用电量

⚠️ **分母是"用电量"不是"发电量"**，两者不能混着比。

**⚠️ 口径警告**：两个消纳率数字含义不同，详见 §5.4。

**`calc_cost` 有多简化？** 它用"平均电价 × 电量"估算，**不考虑分时电价**。
所以它只能给量级参考，真正的电费结论要看方向3 的优化结果（用真实分时电价）。
该估算还有两个已知简化：① 不区分峰谷时段；② 光伏收益按自消纳量 × 均价算，
未计上网收益。

### 8.6 `forecasting/` —— 方面1 源-荷预测

| 文件 | 内容 |
|---|---|
| `forecast.py` | 主流程：季节朴素 + XGBoost 融合；`_metrics` 算 4 个指标；`run_realtime_adaptive` 实时修正 |
| `deep.py` | 深度学习基线：LSTM / Transformer / N-BEATS |
| `benchmark.py` | 多方法对比 + 消融 + walk-forward 交叉验证 |

**预测公式**：

$$
\hat y_t = \max\!\left(0,\; \tfrac12 \bar y_t^{\text{naive}} + \tfrac12 \hat y_t^{\text{ML}}\right)
$$

**四个评价指标**（`_metrics`）：

| 指标 | 含义 | 陷阱 |
|---|---|---|
| MAE | 平均绝对误差，单位同原数据 | 直观，但不反映大误差的严重性 |
| RMSE | 均方根误差，单位同原数据 | 放大大误差；**最适合本项目** |
| MAPE | 平均绝对百分比误差 | **夜里光伏≈0 会把百分比放得极大**，必须过滤小值时段 |
| **相对 RMSE** | RMSE ÷ 装机容量 | **申报书指标就用这个**，可跨目标比较 |

**预测值裁剪到非负（物理约束）**：XGBoost 原始 PV 预测在测试集有 57% 小时为负值
（最小 −33.65 kWh，夜间真值=0 时模型输出小幅负数）。负预测会：
①虚增 MAE/RMSE 指标；②在实时比值修正中 `prev_fc<0` 会使修正方向反转。
现于三处预测出口（`predict_col` / `run_realtime_adaptive.day_ahead` / `adaptive_pv` 逐时）
统一 `max(0, ·)` 裁剪。修复后 PV MAE 154.64→153.67。

**申报书指标达成情况**：`预测月均 RMSE < 20%`
- PV 相对 RMSE **13.21%** ✅ **达标**
- 负荷相对 RMSE **43.19%** ❌（但这是**数据分辨率限制**，非模型失效，见 §5.5）

**实时修正的价值**（演示日实测）：

```
日前预测平均误差 = 168.94 kWh
实时修正后        = 35.79 kWh   ← 降 79%
```

**`run_realtime_adaptive` 的数据泄漏已修复**：
早期版本在生成"日前计划"基准时，用**演示日自身数据**训练 ML 模型（`ml_model.fit(demo_day_df...)`），
导致日前预测"偷看"了它本应预测的未来值，人为压低日前误差约 12 kWh（115.98 vs 真 128.33）。
修正后改为用 **演示日之前的历史**训练（`df_feat[df_feat.index < demo_day_df.index[0]]`），
确保日前口径是"真日前"（不含未来信息）。

**消融实验（ablation）**：像"拆机器"一样逐个拿掉部件，看成绩是否下降。
如果拿掉某部件成绩不变，说明这个部件没用，不该写进论文。

**walk-forward 交叉验证**：训练窗口随时间**扩张**，每次只用"该时刻之前"的数据训练。
比随机切分更贴近真实使用场景，且避免**数据泄漏**。
> ⚠️ `split_train_test` 必须取**最后一段**做测试集，不能随机抽。
> 随机抽会让"未来"信息漏进训练集，精度虚高，答辩时会被抓。

### 8.7 `optimization/` —— 方面2 能-碳调控（核心）

#### `dispatch.py`

| 函数 | 作用 |
|---|---|
| `solve_dispatch()` | **MILP 精确求解**（PuLP/CBC），含买卖互斥 Binary |
| `solve_dispatch_lp()` | **LP 快速求解**（scipy linprog），无互斥约束 |
| `_heuristic_dispatch()` | 启发式兜底（求解器全不可用时） |
| `baseline_no_storage()` | 不装储能的对照 |
| `run_day_ahead_stochastic()` | 日前随机规划（多场景期望） |
| `run_real_time_robust()` | 实时滚动 MPC + 鲁棒余量 |
| `print_optimize_summary()` | 打印对比结论 |

**决策量（每小时一个）**：买电量 `b_h`、卖电量 `s^g_h`、充电量 `c_h`、放电量 `d_h`、电池 SOC `s_h`，以及二元变量 `y_h`

**约束（4 条）**：
1. 功率平衡：`光伏 + 买入 + 放电 = 负荷 + 卖出 + 充电`
2. SOC 边界：`10% ≤ SOC ≤ 90%`
3. 充放电功率上限：`≤ 500 kW`
4. 电池递推：`SOC(t+1) = SOC(t) + η·充电 − 放电/η`

**目标函数**：

$$
\min \sum_{h} \Big[ \pi_h b_h - p^{\text{sell}} s^g_h + \lambda \gamma_h (b_h - s^g_h) \Big]
$$

即"电费 + 碳成本"合成一个统一的"能-碳"目标。其中 λ=0.05 元/kgCO₂。

**两个时间尺度**：
- 日前（day-ahead）：提前一天算计划，用的是**预测值**；五个场景（名义、±10% PV、±5% 负荷）独立求解，报告期望成本与标准差
- 实时（real-time MPC）：真数据来了滚动修正

> 💡 **MPC 就像开车**：眼睛看前方路况（预测未来），手握方向盘（决定这一刻怎么动），
> 每开一小段就重新看一眼路（滚动更新），而不是出发前把全程方向打死。

**🔑 为什么需要 LP 快版？**

| | MILP | LP |
|---|---|---|
| 显式互斥约束 | 有（Binary 变量） | 无 |
| 单次耗时 | 几百毫秒 | 毫秒级 |
| 用途 | 30 天抽样校验 | 219 天 + 上千次敏感性扫描 |

**LP 与 MILP 为何等价？（关键在凸性）**

成本函数对"净交换量 `g = 买 − 卖`"是分段线性：
- 当 `g > 0`（净买）：成本 = 买电价 × g
- 当 `g < 0`（净卖）：成本 = 上网价 × g（负值，即收益）

这段分段函数的斜率从"买电价"跳到"上网价"。**只要斜率是递增的（即上网价 ≤ 买电价），
函数就是凸的**，此时最优解自动满足"同一时刻不会又买又卖"，
所以 LP 松弛和 MILP 得到**同一个解**。

> ⚠️ **这正是 `GRID_SELL_PRICE_YUAN_PER_KWH = 0.39 ≤ 谷段 0.420` 这条配置约束的真正作用。**
> 如果上网价高于最低零售价（例如用真实的 0.8479），就会形成"谷时买 0.420、转手卖 0.8479"
> 的**套利窗口**，成本函数对净交换量 g 变**凹**，LP 会算出发散的假解（同时大量买和大量卖，物理上不可能）。
>
> 📌 注：真实光伏结算单的结算单价确实是 0.8479 元/kWh，但那是"全额上网"口径；
> 本项目做的是"自发自用余电上网"，等价上网价值应锚定燃煤基准价 0.3932 元/kWh。

**实测验证**（n=30 天）：成本差 **max 1.857% / mean 0.062%**，年度结果差异 0.000% ✅

**LP 求解状态检查**：原来忽略 `prob.solve()` 返回状态——若 LP 不可行或 CBC 求解失败，
变量值是无意义垃圾（实测不可行示例仍返回 varValue=5.0），会静默流出"垃圾调度"伪装成最优解。
现增加 `prob.status != LpStatusOptimal` 检查：非最优即告警并退回启发式调度。

**MPC 鲁棒余量曾加错时段（幻影购电）**：鲁棒余量 `robust_load_margin` 经 `solve_dispatch`
被加到**全部 24 小时**（含已发生的真实小时），导致执行动作对真实负荷失衡——每小时凭空多买
`margin×load` 的"幻影电量"真实负荷根本没消耗。审计实测：鲁棒 MPC 最大失衡 120 kWh
（与 `0.05×load` 相关性 1.000），幻影折价 ~1374 元占成本差（1705 元）的 80%。
修复：MPC 中 margin 只写入**未来时段**（`load_nom[t+1:] * (1+margin)`），
给 `solve_dispatch` 传 `robust_load_margin=0`。修复后鲁棒 MPC 失衡归零。

**已知建模限制（未改）**：`solve_dispatch` 未强制"日末 SOC 回到初始 SOC"的循环约束。
日前开环单解会把 `soc_init`（默认 50%×容量）当作当日可调度资源、且不要求日末补回，
极端参数下可能出现"消耗初始电量套利"的虚高收益（手工样例 cost 可为负）。
MPC 滚动场景每步追踪真实 SOC、不存在凭空套利。
真实 EMS 落地时应加日循环约束或 SOC 成本项；本演示量级下影响很小
（代表日净碳排仍降、成本仍省）。

**🔑 bootstrap 置信区间：为什么要按【日】重采样？**

bootstrap（自助法）的思路：从已有样本里**有放回地**反复抽样，
每次都算一遍统计量，看这些结果散布多宽 —— 散布宽说明结论不稳。

> ⚠️ **关键点：必须按【日】重采样，不能按【小时】。**
> 因为同一天里各个小时的误差是**相关的**（这天预测偏乐观，那 24 小时会集体偏）。
> 如果按小时打散重采样，等于假装每小时是独立的，
> 会**低估**真实不确定性，把置信区间算得过窄、结论显得比实际更可靠。
> 这是一个很容易犯、且审稿人会抓的错误。

**全年滚动评估结果**（n=219 天）：

| 电费节省 | **5.1768%** | [4.158, 6.582] |
| 碳排降低 | **3.4953%** | [1.036, 7.604] |

### 8.8 `mining/mining.py` —— 方面3 数据挖掘 + 云边框架

| 函数 | 作用 |
|---|---|
| `mine_typical_days()` | KMeans 聚类把 365 天压成 K 个典型日 |
| `analyze_correlation()` | 源-荷整体 + 逐小时相关性 |
| `detect_anomalies()` | z-score 异常日检测 |
| `simulate_cloud_edge()` | 云边协同框架完整演示 |
| `print_framework_summary()` | 打印汇总 |

**为什么"典型日聚类"在工程上真的有用？**
不是为了论文好看，而是省算力：全年 365 天天气其实就几种模式，
归纳成 8 个典型日后，解 8 次优化就能覆盖绝大多数情况。
这正是云边架构里"云侧做重活"的真实做法。

**KMeans 是什么？** 分两步循环：
① 先随便挑 K 个点当"堆主"；② 每个数据点归到最近的堆主；③ 每个堆重新算中心点；
重复 ②③ 直到中心点不再动。本项目用 24 维（每天 24 小时）的发电形状做聚类。

**实测结果**：8 个典型日，各簇天数 `{0:21, 1:54, 2:31, 3:41, 4:8, 5:22, 6:13, 7:29}`
源-荷整体相关性 r = **0.637**（正相关，同涨同跌 → 就地消纳相对容易做）

**相关系数怎么读？**
- `r = +1`：完全同涨同跌
- `r = 0`：毫无关系
- `r = −1`：完全反向

**⚠️ z-score 异常检测的已知局限**：均值/标准差本身会被异常值带偏。
更稳健的做法是用中位数 + MAD（当前 219 天尺度够用，但换小样本时要注意）。

**云边分工**：
```
云端（离线、算力强）          边端（现场、实时）
  ├ 大数据挖掘：8 个典型日      └ 实时执行：MPC 滚动修正
  ├ 预测：训练源-荷模型                 + 鲁棒余量
  └ 日前计划：随机规划          ◄── 日前计划下发
                               ──► 实时反馈
```
> 为什么这么分工？两类活性质不同：云端能等（可以跑几小时），
> 边缘设备算力小、要秒级响应。所以把重活放云端离线做，边缘只做轻活。

**⚠️ 一个容易忽略的使用建议**：每次换新数据后，**先看 `detect_anomalies` 报了哪些日子**。
如果混着"某天只抄到 500 度电"这种脏数据，年用电量、典型日聚类、优化结果全都会被污染。

### 8.9 `carbon/carbon.py` —— 碳核算

| 函数 | 作用 |
|---|---|
| `grid_carbon_of_buy()` | 买电碳排 = Σ(买电量 × 时变碳因子) |
| `net_grid_carbon()` | 净碳排 = Σ((买 − 卖) × 碳因子)，**与 dispatch 同口径** |
| `carbon_intensity()` | 碳强度 = 总碳排 ÷ 总用电 |
| `annual_carbon_summary()` | 全年粗略估算（给外行看量级用） |

**⚠️ 一个特别容易搞混的点：电本身不"含碳"**

"一度电排多少碳"（碳因子）不是电的属性，而是**当时电网里在发电的那些电厂平均有多干净**。
夜里核电多 → 碳因子低；傍晚火电顶峰 → 碳因子高。

**为什么要逐小时相乘，而不是"总量 × 平均碳因子"？**
```
逐小时：500 kWh × 0.379 + 500 kWh × 0.476 = 427.5 kg
用均值：1000 kWh × 0.42                    = 420.0 kg   ← 少算 7.5 kg
```
差别看着不大，但**优化的目的恰恰就是"把买电时段从高碳挪到低碳"**，
用平均值就把这个可优化空间抹平了，优化器会失去减碳动力。

**碳排口径已修正为"净购电"（范围2 市场法）**：
`dispatch` 与 `carbon.net_grid_carbon` 统一计算
净碳排 = Σ 碳因子 × (买电 − 卖电)，把光伏卖给电网（上网）计为碳信用冲减。
早期版本只算买电碳排、且目标函数漏减卖电，会导致"储能套利卖绿电反而增碳"的反直觉结论
（曾出现优化碳排升 19.1%）；修正后代表日结果为**成本省 19.9% 且碳排降 1.9%**，方向自洽。

> ⚠️ **勿混用**：`grid_carbon_of_buy` 仅算买电侧、不含售电碳信用，
> 不要与优化结论混用。独立的碳报表请用 `net_grid_carbon(buy, sell, carbon)`。

**碳强度 vs 碳排量**：
- 碳排量 = 排了多少（绝对量，kgCO₂）→ 看总量控制
- 碳强度 = 每度电排多少（相对量，kgCO₂/kWh）→ 看效率水平
两个都要看，考核口径不同。

**`annual_carbon_summary` 的注意事项**：默认碳因子已归一到 `config.CARBON_FACTOR_24H` 均值。
它用"买电量 × 平均碳因子"估算，**与逐小时相乘的 `grid_carbon_of_buy` 结果不同**，
只能当量级参考。另外常见说法"1 棵树一年吸 18 kg CO₂"只是形象说法，不要写进论文当数据。

### 8.10 `data/pdf_readers.py` —— 从 PDF 账单抠真实电价

| 函数 | 作用 |
|---|---|
| `_read_pdf_text()` | 读 PDF 全文（读不到就返回 None，不硬猜） |
| `weighted_buy_price()` | 从总账单提取**加权平均买电价** |
| `weighted_sell_price()` | 从光伏结算单提取**上网结算价** |
| `peak_valley_ratio()` | 算峰谷电量比例（用于对账校验） |

**为什么要专门写个文件去抠 PDF？**
① 让每个参数都有出处、可追溯；② 换新账单时能重跑，不用手抄；③ 汇报时可以当众复现。

> ⚠️ **关于 PDF 表格抽取的重要提醒**：PDF 里没有"表格"结构，只有散落的文字块。
> 所以这里是按正则表达式从文本里"捞"数字，而不是解析表格。**抓不到就返回 None，不硬猜。**

**加权均价和算术平均的区别**（为什么必须加权）：
```
100 度 @ 0.50 元 + 10000 度 @ 0.60 元
算术平均：(0.50 + 0.60) / 2 = 0.55 元   ← 错
加权平均：(100×0.5 + 10000×0.6) / 10100 = 0.599 元   ← 对
```
电价是按电量买的，量大才有话语权，所以必须加权。

> ⚠️ **`weighted_sell_price()` 的结果是参考值、不是项目实际使用参数**。
> 它算出 0.8479 元/kWh，但项目实际建模用的是 0.39（见 §8.6 的凸性说明）。
> 该函数可用于"对账/引用"（证明真实结算价是多少），但**不可直接填进 `GRID_SELL_PRICE`**。

**账单正则小数风险（防御性修复）**：`weighted_buy_price` 与 `_bill_monthly_net_purchase`
抓"本期电量"曾用 `([\d,]+)` **漏小数点**，与同文件"本期电费"的 `([\d,.]+)` 不一致；
遍历 26 份真实账单电量全为整数故当前不触发，但换带小数的新账单会静默丢精度。
已将两处统一为 `([\d,.]+)`。

### 8.11 `simulation/model_params.py` —— Simulink 背景参数

**不参与任何数据计算**，只是记录 Simulink 模型 `PV_Microgrid_700V.slx` 的参数。

**为什么要单独建这个模块？**
课题是"光储直柔直流微电网"，Simulink 侧和 Python 侧要讲同一套东西
（母线 700V、低压 48V、三环闭环、MPPT），术语必须一致。
把参数集中放这里，就是那个"对得上"的答辩凭证。

**⚠️ 为什么不做电路仿真？区分两个层次**：

| 层次 | 时间尺度 | 回答什么问题 |
|---|---|---|
| Simulink 层（本模块背景） | 毫秒级 | 控制环稳不稳定？母线电压纹波多大？ |
| Python 层（本项目主体） | 小时级 | 该充多少电？省多少钱？减多少碳？ |

两者时间尺度差 **6 个数量级**（1 ms vs 1 h = 3.6×10⁶ 倍），是互补关系而非同一件事。
靠"参数一致性"衔接（比如母线电压两边都要写 700V）。

> 💡 **顺手记住几个概念**：
> - **Boost = 升压电路，Buck = 降压电路**（名字就是动作）
> - **下垂控制（droop）** 像几个人抬轿子，谁吃劲多谁速度就慢一点，自动分配功率
> - **标幺（per-unit）** 是把物理量除以基准值变成无量纲数，便于跨电压等级比较
> - **占空比（duty）** 是开关管一个周期里导通时间占比

**已知模型状态**：开环母线 699.76 V、纹波 0.016%、193 个模块、三环闭环 + MPPT 已完成。

**参数多为 `None` 是刻意的**：真实值藏在 `.slx` 模块属性里，
写假数字容易被后来的人当真值用，写 `None` 则一眼就知道"还没填"。
提取命令：

```matlab
get_param('PV_Microgrid_700V/Vref_out', 'Value')
```

## 第 9 章 · 关键概念速查

| 术语 | 一句话解释 |
|---|---|
| **消纳率** | 光伏发出来的电，有多大比例被园区自己用掉了（分母是**用电量**） |
| **容量系数** | 实际年发电 ÷ 理论满发年发电，福建正常 12%~22% |
| **日负荷率** | 日均用电 ÷ 最大日用电，越接近 1 越平稳 |
| **SOC** | State of Charge，电池剩余电量占容量的比例，本项目限制在 10%~90% |
| **日前 / 实时** | 提前一天做计划 / 真数据来了滚动修正 |
| **MPC** | 模型预测控制，每走一小段就重新规划一次（像开车看路） |
| **鲁棒优化** | 为最坏情况留余量，宁可多花点钱也要稳 |
| **随机规划** | 用多个可能场景的期望值做决策 |
| **MILP / LP** | 整数线性规划 / 线性规划，后者快但在本问题上与前者等价 |
| **凸性** | 保证最优解唯一且可快速求解的数学性质；本项目靠"上网价≤最低买价"保证 |
| **消融实验** | 拆零件看成绩是否下降，证明各部件贡献 |
| **walk-forward** | 训练窗口随时间扩张，避免数据泄漏 |
| **bootstrap** | 有放回重采样估置信区间，本项目**按日**重采样 |
| **口径** | 统计范围。本项目多处需区分"消纳率表口径"与"园区全量口径" |
| **锚定缩放** | 用可靠的"月总量"当尺子，把不可靠的"小时数据"整体放大/缩小 |
| **净购电** | 从电网买了多少电（= 总用电 − 光伏就地消纳），小时电量表的 `[2]/[3]` 表计记的就是这个 |

**净购电曲线是怎么"还原"出来的（初学者版）**：
1. 小时电量表有每天 24 小时的数字，但它的"倍率没还原"（数值偏小好几倍），不能直接用。
2. 电费账单告诉我们"这个月一共从电网买了多少电"（月总量，可靠）。
3. 把一个月里所有小时的数字加起来，得到"小时表的月示值"。
4. 算一个缩放因子：`缩放因子 = 账单月总量 ÷ 小时表月示值`。
5. 把这个月每天的 24 小时数字都 × 缩放因子 → 量级就对了，且一天内的高低形状保留。
6. 逐月重复，拼成一条"净购电每小时曲线"。运行 `--mode netload` 可看每月还原值与账单的对账。

**两项建模订正（已写入代码并验证，论文正文需说明）**：

   但它 > 谷时零售价 0.420，构成「谷时买 0.42 / 上网卖 0.85」的**非法套利窗口**，
   使调度成本函数对净交换量变为**凹函数**、LP 松弛失效且发散。
   修正为 ≤ 最低零售价（锚定福建燃煤基准价 0.3932），恢复凸性，
   **LP 与精确 MILP 在本问题上严格等价**（详见 §8.6）。
2. **调度求解器改为 scipy linprog 连续 LP**：原 PuLP/CBC MILP 含 Binary 买卖互斥、单次 ~秒级，
   全年 219 天 × 敏感性扫描需数小时；LP 版毫秒级且经校验与 MILP 差异极小（n=30：max 1.857% / mean 0.062%），结论即精确解。

### 10.5 SOTA 对比与消融（扩展研究核心，加分项）

预测粒度选 **日总量**（PV 日发电量 / 负荷日用电量），不受负荷小时形状失真影响，且正好喂给日前/实时调度。

**PV 日发电量**（cap_ref = 1800×24 = 43200 kWh，n_test=105）：

| 模型 | RMSE | MAE | sMAPE | RMSE% |
|---|---|---|---|---|
| **LSTM (no-exo)** | **110.1** | 68.9 | 22.4% | **5.07%** |
| Transformer (no-exo) | 110.3 | 69.2 | 22.5% | 5.08% |
| Transformer | 114.3 | 72.6 | 23.6% | 5.27% |
| **Ours（朴素+XGBoost 融合）** | 118.1 | 76.2 | 24.6% | 5.44% |
| SeasonalNaive（季节朴素） | 120.6 | 78.9 | 25.3% | 5.56% |
| XGBoost | 124.1 | 82.5 | 26.1% | 5.72% |
| N-BEATS | 134.1 | 90.3 | 28.4% | 6.18% |

**消融结论**：PV 日电量里「近期窗口」比「日历特征」有用 ——
带外生的 LSTM/Transformer（5.67%/5.27%）反而不如不带外生（5.07%/5.08%）。
Ours 融合 5.44% 与 SOTA 持平，**未超越**。

**负荷日用电量**（cap_ref = 日均负荷 ≈ 37252 kWh，n_test=61）：

| 模型 | RMSE | MAE | sMAPE | RMSE% |
|---|---|---|---|---|
| **XGBoost** | **11686.1** | 8218.5 | **23.7%** | 30.04% |
| Transformer | 12048.0 | 8735.1 | 24.9% | 30.97% |
| N-BEATS | 13091.2 | 9554.0 | 27.4% | 33.65% |
| Ours（融合） | 13496.3 | 9890.7 | 28.6% | 34.69% |
| SeasonalNaive | 18102.7 | 15790.2 | 42.0% | 46.53% |

**消融结论**：负荷预测里 **日历/外生特征重要**（LSTM 带外生 37.6% vs 不带 46.4%）；
DL 显著优于季节朴素（28.5% vs 43.7% sMAPE）。Ours 融合略逊 Transformer。

> 📌 **诚实提示**：本工程的融合方法在 PV 上不是最优（比 LSTM 差 0.37 个百分点）。
> 论文里应如实报告，并分析原因（融合方法的优势在鲁棒性和可解释性，
> 而非绝对精度），而不是只挑对自己有利的数字。

### 13.3 改完代码后必做的两件事

**① 跑回归，确认没把原来的结果搞坏：**

```bash
python -m pvflex.cli
```

然后对照 §4.3 那张"体检标准表"，**10 行数字必须一字不差**。
只要有一个变了，说明你的改动影响了计算结果 —— 要么是故意的（那就记下来），要么是改错了。

**② 检查有没有误删函数体：**

> ⚠️ 这个项目确实发生过"改注释时不小心把函数内容删掉"的事故。
> 教训：**改 docstring 时，`new_string` 里的函数体必须原样复制。**

有个简单的检查办法（把下面整段复制到命令行执行）：

```bash
python -c "import ast,glob;[print(p,[n.name for n in ast.walk(ast.parse(open(p,encoding='utf-8').read())) if isinstance(n,ast.FunctionDef) and len(n.body)==1 and isinstance(n.body[0],ast.Expr)]) for p in glob.glob('src/pvflex/**/*.py',recursive=True)]"
```

输出里如果某个文件后面跟着 `['某个函数名']`，说明那个函数**只剩注释、没有实际内容了**（被误删）。

**完整的 AST 语法 + 完整性检查脚本**（推荐，输出更易读）：

```bash
python -c "
import ast, glob
for p in glob.glob('src/pvflex/**/*.py', recursive=True) + ['run_extension_study.py']:
    tree = ast.parse(open(p, encoding='utf-8').read())
    empty = [n.name for n in ast.walk(tree)
             if isinstance(n, ast.FunctionDef) and len(n.body) == 1
             and isinstance(n.body[0], ast.Expr)
             and isinstance(n.body[0].value, ast.Constant)]
    print(p, '仅剩docstring=', empty or '无')
"
```

本项目代码由多轮迭代累积，注释风格出现过三种偏差：

1. **时态错乱**：数据源升级后，注释仍停留在旧版本（如"无分时数据"但实际已有 8760h 实测）
2. **量纲不清**：`TYPICAL_LOAD_SHAPE` 的注释没说清它是"占比"还是"电量"，导致误用
3. **只写"是什么"不写"为什么"**：如 `shape = shape / shape.sum()` 不写为何要归一

初学者读代码时，卡住的地方**往往不是语法，而是"这行为什么要这么写"**。
所以规范的重点是：**解释意图，而不只是翻译代码**。

### 14.2 三级注释结构

**第一级：文件头（必须有）**

```
# =============================================================================
# 模块路径/文件名  ——  一句话说明这个文件干嘛的
# -----------------------------------------------------------------------------
# 【这个文件解决什么问题】
#   ……（2~5 行，用大白话讲清它在整个工程里的位置）
#
# 【核心思路 / 关键概念】
#   ……（可选，涉及专业概念时给出通俗解释）
#
# 【输入输出】
#   输入：……      输出：……
#
# ⚠️ 【已知限制 / 注意事项】（有则写，没有可省）
#   ……（如实说明数据口径、数值可靠度、待确认项）
# =============================================================================
```

要求：
- 一句话概括必须让人**不看代码就知道这个文件的作用**
- 涉及专业术语时，**第一次出现必须给通俗解释**
- 有局限的必须如实写，不许回避

**第二级：函数/类 docstring（必须有）**

```python
def 函数名(参数1, 参数2=None):
    """
    一句话说明这个函数做什么（用祈使句，如"读取…""把…转成…"）。

    参数
    ----
    参数1 : 类型
        含义 + 单位 + 取值范围（能写就写）
    参数2 : 类型, 可选
        含义；不传时的默认行为

    返回
    ----
    类型
        含哪些字段/列，单位是什么

    ⚠️ 注意事项（有则写）
        ……
    """
```

要求：
- 参数**必须标注单位**（kWh / kW / 元 / 比例），这是本项目最容易出错的地方
- 返回值的**列名要逐个列出**（下游靠列名取值）
- 抛异常的条件要写明

**第三级：行内注释（关键处必须有）**

只在**三类位置**写行内注释：

| 位置 | 说明 | 示例 |
|---|---|---|
| ① 非直觉的写法 | 为什么不用更直白的方式 | `# 用时间戳查表而非 shift(24)：数据有缺口时 shift 会错位到更早的日期` |
| ② 魔数/阈值 | 这个数从哪来、为何取这个值 | `# 0.10 = 正常的 10%，低于此值判为抄表缺失（经验阈值）` |
| ③ 易错点警告 | 改这里会连带影响什么 | `# ⚠️ 改这里必须同步改 config，否则口径不一致` |

**不要写**：`i += 1  # i 加 1` 这类把代码翻译一遍的废话。

### 14.4 初学者友好的三条写法

**1. 先讲"为什么需要"，再讲"怎么做"**

反面例子：
```python
# 对 shape 做归一化
shape = shape / shape.sum()
```

正面例子：
```python
# 把形状归一化成"占比"（24 个小时加起来 = 1）。
# ⚠️ 为什么必须归一：不同来源给的数组量纲不一样——估算形态是占比，
#    而实测数据是"每小时多少度电"。不归一的话，把 712.8 当成占比用，
#    会让这一小时的负荷被放大成 2772 万度，完全离谱。
shape = shape / shape.sum()
```

**2. 用生活类比解释专业概念**

```python
# MPC（模型预测控制）就像开车：
#   眼睛看着前方路况（预测未来），手握方向盘（决定这一秒怎么动），
#   每开一小段就重新看一眼路（滚动更新），而不是出发前把全程方向打死。
```

**3. 主动指出"这里容易踩的坑"**

```python
# ⚠️ 坑：pd.DataFrame({'a': s1, 'b': s2}) 会按【索引】对齐而不是按位置。
#    如果两个序列的索引长度不同，pandas 会各自补齐 NaN（不会报错），
#    dropna 之后就只剩交集部分——结果可能比预期少很多行。
#    排查办法：打印 len() 看行数是否符合预期。
```
